

# Module 7 Lesson Plan

Naming convention:

```text
M7_V<NN>_<Title>_[F|S|A]
```

Where:

```text
F = Face recording
S = Screen recording
A = Animation / visual explanation
```

---
### Questions you anwer for each concept
- What are we trying to do?
- What problem appears?
- What do we need to solve it?
- What is this called in robotics?
- How does it work?
- How do we implement it?
- How do we know it worked?

## M7_V01_Why_Multi_Robot_Collaboration_After_Perception_[F]

### Purpose

Introduce Module 7 and explain why multi-robot collaboration comes after perception, MoveIt, and pick/place.

### Story question

> If one robot can pick and place objects, what changes when two robots work in the same environment?

### Content

* Review previous modules:

  * MoveIt planning
  * pick/place
  * RGB-D perception
* Explain why one robot is not always enough.
* Introduce multi-robot collaboration.
* Explain simple multi-robot use cases:

  * parallel sorting
  * divided work zones
  * staging-area handoff
  * shared workspace access
* Clearly state that this module has **no AI**.
* Explain that robots will follow rule-based coordination.

### Output

Students understand why Module 7 exists and how it connects to Modules 4–6.

## M7_V02_Multi_Robot_System_Mental_Model_[A]

### Purpose

Give students a clean visual understanding of multi-robot architecture.

### Story question

> What are the main parts of a multi-robot manipulation system?

### Content

Explain this architecture:

```text
shared world
→ robot1
→ robot2
→ shared perception
→ task coordinator
→ zone manager
→ robot-specific executors
```

Explain the difference between:

```text
single robot system
multi robot system
```

```text
own namespace
own TF frames
```

## M7_V03_Namespaces_TF_Prefixes_and_Robot_Identity_[A/S]

### Purpose

Teach the most important ROS 2 concept for multi-robot systems: separation.

### Story question

> How do we stop two robots from publishing the same topics and frames?

### Content

Explain:

* robot namespaces
* TF prefixes
* frame conflicts
* topic conflicts
* controller conflicts
* why `/joint_states` alone is not enough for two robots

Show example:

```text
Bad:
panda_link0
panda_joint1
/joint_states

Good:
robot1/panda_link0
robot1/panda_joint1
/robot1/joint_states

robot2/panda_link0
robot2/panda_joint1
/robot2/joint_states
```

### Output

Students understand why namespaces and TF prefixes are required.

## M7_V06_MoveIt_for_Multiple_Robots_[S]

### Purpose

Show how MoveIt planning works when there is more than one robot.

### Story question

> Does each robot need its own MoveIt pipeline, or can one planner control everything?

### Content

Explain two options.

## Option 1: Separate MoveIt instances

```text
robot1 MoveIt
robot2 MoveIt
central coordinator assigns tasks
```

This is easier for Module 7.

## Option 2: Combined multi-arm MoveIt config

```text
one MoveIt config containing both robots
```

This is more advanced and can be optional.

Recommended for Module 7:

```text
Start with separate MoveIt instances + coordination rules.
```

Explain:

* robot-specific planning group
* robot-specific planning scene
* shared obstacles
* why planning scenes must stay consistent

### Output

Students understand the recommended planning architecture.

## M7_V09_Workspace_Zones_and_Shared_Zone_Locks_[A]

### Purpose

Teach safe workspace sharing.

### Story question

> What prevents both robots from reaching into the same area at the same time?

### Content

Explain:

* private zones
* shared zones
* staging zone
* lock/unlock behavior
* wait state
* conflict prevention

Example:

```text
robot1 requests center_shared_zone
zone manager grants lock
robot2 requests center_shared_zone
robot2 waits
robot1 exits zone
zone manager releases lock
robot2 enters
```

Visualize:

```text
left zone: robot1 only
right zone: robot2 only
center zone: one robot at a time
```

### Output

Students understand simple but powerful multi-robot safety coordination.

## M7_V11_Center_Shared_Zone_Demo_[S]

### Purpose

Show conflict prevention in a shared workspace.

### Story question

> What happens when both robots want to use the same shared area?

### Demo flow

```text
object is in center zone
robot1 and robot2 are both capable of reaching it
coordinator assigns robot1
robot2 waits or receives another task
robot1 completes task
zone lock releases
```

### Content

Show:

* lock request
* lock granted
* second robot blocked
* safe execution
* lock released
* next task starts

### Output

Students understand how resource locks prevent robot conflicts.

## M7_V12_Staging_Area_Handoff_Demo_[S]

### Purpose

Teach collaboration without risky mid-air handoff.

### Story question

> How can two robots cooperate on the same object without handing it directly in the air?

### Demo flow

```text
robot1 picks object from source
robot1 places object in staging zone
robot2 waits for staging zone update
robot2 picks object from staging zone
robot2 places object in final bin
```

### Content

Explain:

* why staging handoff is safer than direct handoff
* staging pose
* task dependency
* robot1 completion signal
* robot2 start condition
* shared zone lock

### Output

Students understand sequential collaboration between two robots.

## M7_V15_Multi_Robot_Evaluation_and_Throughput_[S]

### Purpose

Measure whether using two robots improves task performance.

### Story question

> Does adding another robot actually improve the system?

### Content

Compare:

```text
single robot sorting 6 objects
two robots sorting 6 objects
```

Measure:

```text
total task time
robot idle time
number of completed objects
number of conflicts avoided
number of failed tasks
average task duration
```

Example metrics:

```text
Single robot:
6 objects completed in 180 seconds

Two robots:
6 objects completed in 105 seconds
```

### Output

Students understand how to measure multi-robot system value.
