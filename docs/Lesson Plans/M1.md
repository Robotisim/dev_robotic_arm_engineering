

# Module 1 Lesson Plan

Naming convention:

```text
M1_V<NN>_<Title>_[F|S|A]
```

Where:

```text
F = Face recording
S = Screen recording
A = Animation / visual explanation
```
### Questions you anwer for each concept
- What are we trying to do?
- What problem appears?
- What do we need to solve it?
- What is this called in robotics?
- How does it work?
- How do we implement it?
- How do we know it worked?

## M1_V01_Why_Robot_Description_Comes_First_[F]

### Purpose

Introduce the module and explain why robot description is the foundation before control, IK, planning, or hardware.

### Story question

> Before we control a robotic arm, how does ROS 2 know what the robot looks like?

### Content

* Explain what students will build in Module 1.
* Introduce the stick arm and Panda.
* Explain why we start with robot description.
* Explain that control and IK come later.
* Set the expectation: first we make ROS 2 understand the robot body.

### Output

Students understand the purpose of the module and the bigger learning path.

---

## M1_V02_Workspace_and_Package_Structure_[S]

### Purpose

Show the workspace and explain the role of each package.

### Story question

> Where does each part of the robotic arm system live inside the ROS 2 workspace?

### Content

Explain these packages:

* `robotic_arm_description`
* `robotic_arm_bringup`
* `robotic_arm_sim`
* `robotic_arm_control`
* `robotic_arm_hardware`

Focus mainly on:

* description package
* bringup package
* simulation package

### Output

Students understand the workspace map before opening URDF and launch files.

## M1_V03_Frames_Links_Joints_and_TF_Mental_Model_[A]

### Purpose

Build the visual mental model of a robotic arm.

### Story question

> If a robot has many moving parts, how do we track where every part is?

### Content

Explain:

* base link
* shoulder link
* elbow link
* wrist link
* gripper/end-effector
* link frames
* joint frames
* TF tree
* parent-child relationships
* downstream motion

Use this flow:

```text
base_link → link_1 → link_2 → link_3 → end_effector
```

### Output

Students understand that a robotic arm is a chain of links and joints connected through frames.

---

## M1_V04_URDF_Xacro_and_Robot_Description_Flow_[A]

### Purpose

Explain how URDF/Xacro becomes a robot model inside ROS 2.

### Story question

> How do we write the robot structure so ROS 2 can understand it?

### Content

Explain:

* URDF
* Xacro
* `robot_description`
* `robot_state_publisher`
* TF
* RViz

Use this pipeline:

```text
URDF/Xacro → robot_description → robot_state_publisher → TF → RViz
```

### Output

Students understand that URDF is not just a file; it is the source of truth for robot structure.

## M1_V05_Building_the_Stick_Arm_Xacro_[S]

### Purpose

Teach the simple stick arm model from the Xacro file.

### Story question

> How do we create our first robotic arm using simple shapes?

### Content

Open the stick arm file and explain:

* robot tag
* base link
* links
* joints
* visual geometry
* collision geometry
* inertial tags
* joint origin
* joint axis
* joint limits

The current teaching map identifies `stick_arm_4dof.urdf.xacro` as the main “build a robot from scratch” teaching file.

### Output

Students can read and understand the simple stick arm model.

## M1_V06_Visualizing_the_Stick_Arm_in_RViz_[S]

### Purpose

Launch and inspect the stick arm in RViz.

### Story question

> We wrote the robot description, but how do we know it works?

### Demo command

```bash
ros2 launch robotic_arm_bringup view_robot.launch.py robot:=stick_arm
```

### Content

Show:

* RViz robot model
* joint sliders
* TF frames
* how joint movement updates the robot
* how the robot description becomes visual

### Output

Students can launch the stick arm and move joints in RViz.

## M1_V07_Understanding_the_RViz_Launch_Flow_[S]

### Purpose

Explain what happens when the RViz launch command runs.

### Story question

> What happens behind the scenes when we launch the robot?

### Content

Explain:

* `view_robot.launch.py`
* `stick_arm_rviz.launch.py`
* launch arguments
* Xacro processing
* `robot_description`
* `robot_state_publisher`
* `joint_state_publisher_gui`
* RViz startup

The teaching map describes `view_robot.launch.py` as the main public selector and `stick_arm_rviz.launch.py` as the best file to explain line by line for beginners.

### Output

Students understand launch architecture instead of only copying commands.

## M1_V08_Panda_Model_and_Why_Xacro_Matters_[S]

### Purpose

Show how a real robot model is more complex than the stick arm.

### Story question

> What changes when we move from a simple teaching arm to a real robot model?

### Demo command

```bash
ros2 launch robotic_arm_bringup view_robot.launch.py robot:=panda
```

### Content

Explain:

* Panda Xacro model
* mesh files
* joint naming
* joint limits
* gripper structure
* collision vs visual geometry
* why real robots need Xacro

The Panda model should be used for reading and comparison, not as the first file students edit.

### Output

Students understand how professional robot descriptions scale beyond simple shapes.

---

## M1_V09_Stick_Arm_vs_Panda_Comparison_[S]

### Purpose

Compare the simple and realistic robot models.

### Story question

> Are simple and real robotic arms conceptually different, or just more detailed?

### Content

Compare:

* number of joints
* links
* TF tree complexity
* primitive shapes vs meshes
* simple limits vs realistic limits
* end-effector structure
* launch flow similarity

### Output

Students understand that Panda follows the same robot description pipeline as the stick arm.

---

## M1_V10_Gazebo_Bringup_From_Model_to_Simulation_[S]

### Purpose

Show that the same model can move from RViz visualization into Gazebo simulation.

### Story question

> Once the robot model works in RViz, how do we load it into simulation?

### Demo commands

```bash
ros2 launch robotic_arm_bringup sim_robot.launch.py robot:=stick_arm
```

```bash
ros2 launch robotic_arm_bringup sim_robot.launch.py robot:=panda control:=false
```

### Content

Explain:

* RViz vs Gazebo
* simulation world
* model spawning
* Gazebo resource paths
* simulation time
* why workspace sourcing matters

Use Gazebo only for bringup validation here, not deep control.

### Output

Students can bring up both robot models in simulation.

---

## M1_V11_Validation_TF_and_Common_URDF_Fixes_[S]

### Purpose

Teach students how to debug common model problems.

### Story question

> If the robot appears broken, how do we find the problem?

### Content

Debug:

* missing link
* wrong parent-child relationship
* wrong joint axis
* wrong origin
* broken TF tree
* mesh not loading
* joint slider not moving expected link
* wrong joint name

Use this flow:

```text
Build → Source → Launch → Check terminal → Check RViz → Check TF → Check joint sliders
```

### Output

Students can validate and debug their robot model.
